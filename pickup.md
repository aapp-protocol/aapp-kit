- [ ] Configuration Profiles & Test-Gate Recipe (for P-56's cookbook): an advisory recipe (e.g. `docs/recipes/getting-started/configuration-profiles.md`) with copy-paste `git config` blocks and a one-line reason per key for four intended uses: solo human-led; one agent, one checkout; several agents in parallel (plan worktrees, `integrate`, strict attribution, quarantine); team with pull requests (`integrate hook`). `aapp.planSession` stays personal, outside every profile. Plus a recipe for registering P-60's `pre-done` test gate (hash, registry line, timeout). Docs only; fold into P-56.
- [ ] Configuration Manager CLI (`aapp config`): Add manifest-backed `config.tsv` and `aapp config` command (`list`, `get`, `set`) with type validation to inspect and manage `git config aapp.*` repository settings.
- [ ] Work Dispatch Queue for Multi-Agent Execution (`aapp dispatch` / `aapp queue`): In multi-agent environments implementing multiple plans concurrently across isolated worktrees, a central work dispatch queue would coordinate which agent claims which plan. Currently, `state_matrix.md` defines the human priority sequence, but there is no automated worker claiming/leasing mechanism (`aapp next` / `aapp claim`) or queue tracker to allocate frozen, unblocked plans to idle agents without collisions or duplicate effort. Explore introducing a lightweight queue/workpool protocol. Also covers integration: merge finished plans into `develop` one at a time, keeping both sides of `CHANGELOG.md` conflicts, stopping only on real code conflicts (from the P-48 rework). *Not carried in P-54: automatic worktree removal (with safeguards for untracked/ignored files), worker claiming/leasing, and sequential branch integration. Those stay with this Work Dispatch Queue pickup idea (RFC P-52/P-54).*
- [ ] Autonomous Blast-Radius Lease Negotiation & Quarantined Handoff: When an autonomous or unattended agent hits an out-of-bounds file collision caused by an intentional clean break (e.g. legacy test suites breaking on new fail-closed invariants), unattended execution cannot prompt a human. Explore a structured negotiation protocol: (1) requesting a signed out-of-band blast-radius lease expansion from an evaluator/orchestrator, or (2) executing a Quarantined Partial Handoff (committing in-bounds changes proven green under unit isolation, reverting the out-of-bounds collateral file, and emitting an automated regression handoff ticket). Long-range capability for autonomous agent fleets.
- [ ] Reserved ID Blocks: provider plugin pre-reserves plan/issue IDs so allocation works while it is unreachable. Design: P-32 Q5.
- [ ] Layer-0 Enforcement Practice & Unsupervised Agent Security Manual (docs only, not kit code): the kit's guards keep cooperating humans and agents on protocol; they do not stop a determined or unconstrained actor with raw shell access (e.g. any agent running arbitrary bash could edit files without sudo checks or send a started/blocked plan back to Refining by hand, #104). Author a comprehensive high-assurance deployment manual for unsupervised agents running on servers and security-critical enterprise environments: (1) externalized tool boundaries: the `aapp` binary and runtime engine live strictly outside the repo (`/usr/local/bin/aapp` and `~/.local/share/aapp-kit/`), completely out of reach of agent workspace tools; (2) OS-level permission hardening: separate OS users and file ownership (`chown root:root` / `chmod 644` or `chmod 755`) for `.githooks/`, `.git/hooks/`, and `.agents/skills/aapp-hooks/registry.tsv`, ensuring that even raw shell scripts fail at the kernel VFS level with `EACCES (Permission denied)` if attempting to alter pinned hook SHAs without `sudo`; (3) container isolation: mounting governance directories and hooks as read-only volumes (`:ro`) in containerized agent runners (Docker/K8s); (4) architectural role separation: planning in one isolated worktree/machine and developing in another with separate agents; a read-only plans worktree for coding agents, with issue reporting delegated through audited hooks; (5) server-side branch protections and push-validation gates on the `plans` and `develop` branches. The kit must keep functioning seamlessly under these restrictive OS permissions; verify this compatibility and document the full 5-tier defense-in-depth trust model.
