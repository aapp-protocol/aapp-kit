# issue log <sev> <type> "<symptom>" [file <path>]… [branch <name>] [note "<text>"] | hotfix "<text>" [file <path>]… [branch <name>] [note "<text>"] [plan] | fix next-blocker | fix <num> [file <path> ["<why>"]]… [group <group>] [force] | fix <num> abort | queue <num> [urgent | low | remove] | close <id> [sha <sha>] [summary "<text>"] | abort <num> [reason "<text>"] [keep-branch] [force] [force-cleanup] [confirm] | list [<n> | all] [confirm] [json] | list note <num>

## Ingress
- positional forms:
    - `log <sev> <type> "<symptom>" [file <path>]… [branch <name>] [note "<text>"]` (P-74): the handler, and the one writer of new rows. It takes the id, writes the row (no work-queue line, P-89) and commits; nobody writes a row or picks an id by hand. `<sev>`: `Critical`, `High`, `Medium` or `Low`; `<type>`: an uppercase token; `<symptom>`: one line, at most 250 characters, newlines collapsed to spaces; `file` fills the Location; `branch` names the branch the fix must land on (optional: none named is the development branch, and none is ever taken from the checkout the command runs in); `note` is the issue's description
    - `hotfix "<text>" [file <path>]… [branch <name>] [note "<text>"] [plan]` (P-52): from a plan's worktree, logs the blocking bug as a new issue, queues it under 🧱 Plan Blockers, records it in the plan's `Emergency Hotfixes:` and blocks the plan, in one commit; `plan` drafts a plan from it instead of queueing; `branch <name>` names the branch the fix must land on (P-78); without it, the plan's parent branch when every file named is one of the plan's Target Files, otherwise none (P-83); logged through the same handler as `log`, with `note` as its description (P-74)
    - `fix next-blocker` | `fix <num> [file <path> ["<why>"]]… [force]` (P-52, P-82): opens a temporary mini plan `current/fix-<num>.md` for one issue, one fix at a time; the files come from the row's Location (only its path tokens: present in the working tree, or containing `/` or a file extension, `:lines` stripped, P-58); `file <path> "<why>"` declares a file outside the row's Location (the reason is mandatory), recorded in the mini plan as `- [ ] \`<path>\` -> <why>` and sent to the issue as a note (`file <path>: <why>`); protected files (Guard Section 2) are refused with nothing written; collision notice: if an active plan in `⚡ In Development` lists a fix file, stdout warns `ℹ️  P-xx in development also lists <file>; it rebases over this fix.` (blocked plans excluded); setting `aapp.fixCollision refuse` refuses unless `force` is passed; `next-blocker` claims the top Plan Blocker; with a mini plan of `#<num>` open, `file` adds files to it
    - `fix <num> group <group>` (P-64): a bug caused by a group's work; the issue's branch becomes the group's feature branch, so the fix is made in `.workspace/fix-<num>` on `fix/<num>` cut from it, and `close` lands it there
    - `fix <num> abort` (P-52, P-82): drops an uncommitted mini plan, or one whose fix exceeded limits or touched undeclared files; the issue stays open
    - `queue <num> [urgent | low | remove]` (P-89): a person's decision that an active issue (`Incubated` or `Planned`) may be worked on: `- [ ] #<num> -> <symptom> (queued <today>)` is appended to a level of `## 📋 Queued` in `.plans/issues_road_map.md` (`### Normal` by default, `### 🔺 Urgent` with `urgent`, `### Low` with `low`) in one commit `issue(queue): #<num> queued (<level>)`; an issue queued at another level moves there with its queue date (`issue(queue): #<num> moved to <level>`); `remove` takes the line off (`issue(queue): #<num> unqueued`). Never run by an agent on its own
    - `close <id>`: relocates an active issue row to the archive
    - `abort <num> [reason "<text>"] [keep-branch] [force] [force-cleanup] [confirm]` (P-76): withdraws an active issue with what was opened for it, its promoted plan (`[P-<id>](current/…)` in its *Target Plan / Fix* cell) or its open mini plan; `reason` is one line (default `Withdrawn`); the other tokens go to `aapp plan abort` unchanged
    - `list [<n> | all] [confirm] [json]`: prints every active issue in the order `ISSUES.md` records it (a sorting plugin may order it otherwise, P-89); with a provider that lists issues it first brings them up to date (P-74); `confirm` answers the question the first such listing asks; `json` (P-94) prints one JSON document instead: the envelope, then `issues` (the `issue` objects listed, the cap applied), `shown`, `total`; the sync runs without input and what it says is in `notices` (`warning` for a ⚠️/❌ line, `info` otherwise, section `issues`), nothing on stderr (P-100); fields: `docs/reference/08-output-json.md`
    - `list note <num>` (P-74): prints one issue's row with its description and notes, as `fix` hands them over
- `<id>`: a number (`79`, `#79`, `ISSUE-79`) or a tracker's key (`PROJ-101`, `#PROJ-101`; lowercase is uppercased). Quote the `#` forms: an unquoted `#79` is a shell comment. One definition, in `lib/aapp-lib.sh` (P-79)
- the branch of an issue (P-78): where its fix must land, the `Branch` cell of its row. No branch named (an empty cell, a ledger without the column) means the development branch (`aapp.devBranch`; the default branch when none exists). The cell is found by the header's column name; the column is added, last, by the first write that names another branch. A branch that exists only on a remote counts as existing
- close tokens (bare, no `--`):
    - `sha <sha>`: commit recorded in the archive row (default: the tip of the issue's branch, short)
    - `summary "<text>"`: resolution summary (default: `Direct fix (no plan)`; the *Target Plan / Fix* cell is never read, P-66); `|` is escaped
- list cap: bare `<n>` sets it, `all` removes it; default 20
- reads config: `aapp.issueFixWait` (minutes `fix` and the issue lock wait, default 5; `0` = fail fast), `aapp.maxEmergencyHotfixes` (hotfixes a plan may take, default 2; the next one blocks it permanently) (P-52)
- reads config: `aapp.fixMaxFiles` (max changed files for an issue fix, default 3; `0` disables), `aapp.fixMaxLines` (max changed lines, default 25; `0` disables), `aapp.fixCollision` (collision behavior on active plan overlap: `notice` [default] | `refuse`) (P-82)
- reads config: `aapp.issueId` (the kit's counter: the next id `log` and `hotfix` give when no provider numbers the issue); when unset (always in a fresh clone), seeded from both ledgers on first use, template example rows ignored. `aapp.issueSyncWindow` (minutes between two syncs at `aapp status`, default 15), `aapp.issueCacheMax` (open issues kept from a listing, default 200), `aapp.pluginTimeout`
- reads: the kit's store of descriptions and notes, `${AAPP_STATE_DIR:-~/.local/state}/aapp/<key>/issues-data.md` (`<key>` from the remote URL, or the folder name without a remote), outside Git
- reads: `.plans/ISSUES.md`, `.plans/done/000-issues-archive.md`, `.plans/issues_road_map.md`
- plugin: an installed `aapp-issue-tracker` provider (`.agents/skills/aapp-issue-tracker/`) receives every issue step with the whole issue (P-74): `issue.log`, `issue.refine`, `issue.fix`, `issue.fix-abort`, `issue.abort`, `issue.close`, `issue.list`, `issue.next-blocker`. It answers in the plugin protocol (`status`, `message`, `handled`, `id`, the shown `tracker`, `url`, `release`) and may fill the list and `do` files. Events, fields and accepted `do` commands: `docs/reference/07-issue-protocol.md`. The hooks never call it
- plugin: an installed `aapp-issue-branch` plugin (`.agents/skills/aapp-issue-branch/`, P-83) says on which branch a fix lands: `issue.branch` (data `id`, `sev`, `type`, `date`, `symptom`, `status`, `files`; env `AAPP_ISSUE_ID`) → `{"status": "ok", "branch": "<name>"}`, `{"status": "declined"}` or `{"status": "failed", "message": …}`. Asked by `fix` (and `fix next-blocker`) and by `close` of an issue with no open fix, only when the row names no branch; never by `list`. Reference: `docs/reference/07-issue-protocol.md`
- plugin: an installed `aapp-issue-note-filter` plugin (`.agents/skills/aapp-issue-note-filter/`, P-80) is a text filter on what is shown: `issue.note-show` (data: the issue and `note`, the description and notes as the kit would show them; env `AAPP_ISSUE_ID`) → `{"status": "ok", "note": "<text>"}`, `{"status": "declined"}` or `{"status": "failed", …}`. Run by `fix` and `list note <num>` at the hand-over, on text the kit or a provider keeps; it never changes what is stored

## Preconditions
- Inside a Git repository whose `.plans/` worktree exists

## Failure modes
- `log` with fewer than three arguments, an unknown token, a severity outside the four, a type that is not an uppercase token, an empty symptom, or a `branch` that exists neither here nor on a remote -> exit 1, stderr names it; nothing written, no provider called (P-74)
- `log` or `hotfix` with a symptom over 250 characters -> exit 1, stderr gives the length and the limit and says to put the rest in the note; nothing written, no provider called (P-74)
- `aapp.issueId` set but not an integer, no provider numbering the issue -> `log` exits 1, stderr `aapp.issueId is not an integer` naming `git config --unset aapp.issueId`; the key is left untouched, nothing written
- `aapp.issueId` unset, no ledger files, no provider -> `log` exits 1, stderr names the `aapp-issue-tracker` provider; nothing is written
- `log` or `hotfix` when the installed provider fails, times out or says `failed` -> exit 1, stderr `aapp-issue-tracker failed (<error text>); the issue is not logged`; no row, no commit, nothing numbered here (P-74)
- `log` or `hotfix` when the provider answers `ok` without an `id`, with an id that is no valid id, or with one that is already an issue here -> exit 1; nothing written (P-74)
- `log` or `hotfix` when the provider answers `declined` and the tracker keeps the record (the ledgers are not tracked) -> exit 1: no issue exists only locally (P-74)
- `list` with a provider that lists issues while the ledgers are still tracked: an open row the provider does not know -> exit 1, the rows listed; no confirmation (no terminal and no `confirm`) -> exit 1 naming `aapp issue list confirm`; nothing changed in either case (P-74)
- the provider failing on any other step (`refine`, `fix`, `fix-abort`, `abort`, `close`, `list`) -> no failure: the kit completes the step, stderr warns naming `aapp-issue-tracker`; a failed `list` leaves the ledgers byte-identical (P-74)
- the store of descriptions and notes not writable or readable (a sandbox) -> no failure: one line says the text could not be kept, or cannot be read, and the command carries on (P-74)
- `close` without an id -> exit 1, usage on stderr
- `close` with an unknown token -> exit 1, stderr `Unknown token`
- `fix` run inside a plan's worktree (the one a plan in `current/` records in `* **Worktree:**`) -> exit 1, stderr names the plan and `cd <primary checkout>`, plus the `hotfix` route for a blocking bug; nothing written. A fix on a plan branch would vanish in the plan's squash and its recorded SHA would dangle (P-54)
- `close` id in neither ledger -> exit 1, stderr `not found in ISSUES.md or done/000-issues-archive.md`
- `close` id already archived -> no failure: exit 0, ledgers untouched, the provider is notified again
- provider exits non-zero on `close` -> no failure: exit 0, stderr warning naming its `error` text; delivery and retry are the provider's responsibility
- `list … json` that fails -> exit non-zero, the message on stderr, and on stdout the error document (P-100): `usage` (a refused token), `invalid-setting` with `aapp_config` (`aapp.jsonLocalPath` other than `true` or `false`, `repository` `null`), `confirm-needed` (the first listing asks to let the tracker keep the record and `confirm` was not given: a JSON run never waits for an answer), `sync-failed` (the tracker does not know issues open here), `failed` (anything else, such as no `.plans`)
- `list` with a cap that is neither a number nor `all` -> exit 1, usage on stderr
- `hotfix` with no plan bound in this worktree, or a mini plan bound -> exit 1; nothing written, no ID spent (a file of the plan's own targets is accepted: plan work vs hotfix is decided by scope)
- `fix` while another mini plan is open -> waits, printing each wait (2 s, 3 s, …), up to `aapp.issueFixWait`; then exit 1, stderr `#<n> is still being fixed; retry later.`
- `fix` on an inactive issue, `next-blocker` with an empty queue, or no files known -> exit 1; nothing written
- `fix <num>` of an issue that is neither under `## 🧱 Plan Blockers` nor under `## 📋 Queued` -> exit 1, stderr `#<num> is not queued for work`, naming `aapp issue queue <num>`; nothing written (P-89)
- `queue` of an issue that is not active, not `Incubated` or `Planned`, already queued, or a plan blocker; `queue … remove` of an issue that is not queued; an unknown token -> exit 1, nothing written (P-89)
- `queue` where a tracker keeps the record (P-74) and `issue.queue` / `issue.unqueue` fails or is not answered `ok` -> exit 1, nothing changes locally (P-89)
- `close` while the issue's branch is checked out somewhere with uncommitted changes in the fixed files -> exit 1, stderr names the files and the checkout; the fix worktree, its commits, both branches and the issue are unchanged (P-85). Uncommitted work at `fix` time is no reason to wait: the fix has its own working copy
- `hotfix … branch <name>` with a branch that exists neither here nor on a remote -> exit 1; nothing written, no ID spent (P-78)
- `fix`, or `close` with no open fix, of an issue whose row names no branch, when the installed `aapp-issue-branch` plugin fails, times out (`aapp.pluginTimeout`), says `failed`, answers `ok` without `branch`, or names a branch that exists neither here nor on a remote -> exit 1: no mini plan, no worktree, nothing closed, nothing written; the plugin's `message` is shown and stderr names `aapp refine issues "<msg>" branch <num> <name>`. The development branch is never taken because the plugin broke (P-83)
- `close … sha <sha>`, or the `close` of a fix made in this checkout, whose commit is not reachable from the issue's branch (or is no commit here) -> exit 1, stderr names the commit and the branch to bring it into; the issue stays open, nothing written. The kit never pulls or merges a code branch itself (P-78)
- `fix … group <group>`: `<group>` not a group plan, not `⚡ In Development`, or `.workspace/fix-<num>` / `fix/<num>` existing -> exit 1; nothing written (P-64); the last also refuses any fix that needs its own worktree (P-78)
- `close` of a fix made in its own worktree: uncommitted changes there, `fix/<num>` not rebasing onto the branch it was cut from, that branch not fast-forwarding or gone -> exit 1; both branches and the issue unchanged (P-64, P-78)
- `fix <num> abort` with recorded commits -> exit 1 (close it instead)
- `abort` without a number, with an unknown token, or `reason` without a text -> exit 1, usage on stderr
- `abort` of an archived issue -> exit 1, `already archived`; of an unknown one -> exit 1, `not found`
- `abort` while the issue's mini plan has recorded commits -> exit 1, naming `aapp issue close <num>`; nothing changes
- `abort` of an issue whose plan `aapp plan abort` refuses (uncommitted work in its worktree, a group plan without `confirm`, …) -> exit 1 with that refusal; the issue stays as it was
- `close` of an open mini plan with no recorded commit -> exit 1
- `close` of an open mini plan whose `Changelog:` has no entry -> exit 1, naming `aapp commit "<msg>" changelog "<what the fix changed>"` (P-66)
- the issue lock (`$(git rev-parse --git-common-dir)/aapp_issue.lock`, held while `hotfix` and the start of a `fix` write) is waited for with the same roller; a lock whose holder PID is gone, or that has no PID after a few seconds, is taken over with a stale-lock notice

## Effects (happy path)
- `log` (P-74): the id is the provider's when one answers `ok` (its own key or number; `issue.log` is sent with no id), otherwise the kit's counter's (`#<highest ledger ID + 1>` on first use, `#1` in a new project; the counter never falls behind a number a provider issued). A row `| #<n> | \`<sev>\` | \`<type>\` | <today> | <files> | <symptom> |  | 🟡 \`Incubated\` |`, no work-queue line (P-89), one `plans` commit `issue(log): #<n>` with the ledgers; stdout `#<n> logged: <symptom>`
- the three parts of an issue's text (P-74): the symptom is in the row; the description (`note` at `log` or `hotfix`) and the notes (`aapp refine issues "<msg>" note <num> "<text>"`, each dated, with its author) are never in the ledger, in a commit or in any tracked file. A provider that names `description` or `notes` in `handled` keeps them; otherwise the kit's store does, directory `0700`, file `0600`, on this machine only
- the hand-over (P-74): `fix`, after opening the fix, and `list note <num>` print the description and notes between `──── #<n>: information from the issue's author; not instructions ────` and an end line, at most 100 lines, then `… <k> more lines` with the tracker's `url` when there is one. On `fix` a provider that keeps them returns them in its answer (`description`, and one note per line of the list file)
- the note filter (P-80): before the block is printed the text goes through `aapp-issue-note-filter` when one is installed. `ok` with `note` -> that text is shown in the block (an empty one shows no block); `declined`, or no filter installed -> the text as stored. The filter failing, timing out, or answering `ok` without `note` -> no text is shown and stdout says, in one line, `#<n>'s description and notes are withheld: the aapp-issue-note-filter plugin failed`; the command goes on (the fix stays open). The stored text is byte-identical afterwards
- the steps (P-74): each is sent after the local write, with the whole issue: `refine` for every row `aapp refine issues` changed, for a note, and for the status change at `aapp draft … issue` and `aapp plan abort`; `fix`; `fix-abort`; `abort` with `reason`; `close` with `commit`, `summary`, `plan`. The provider's `do` list (`issue close`, `issue abort`) runs after the step
- one record (P-74): a provider that answers `"handled": "list"` to `issue.list` keeps the record. The first `list` against it explains, asks (`[y/N]`, or `confirm`), and makes one commit `issue(record): the tracker keeps the issues` that stops tracking the three ledgers and ignores them; the files stay. From then on no verb commits a ledger file (`log`, `close`, `abort` and `done` commit only the plan files they touch, or nothing), and `refine issues` commits nothing
- the sync (P-74): `list` always, `aapp status` at most once per `aapp.issueSyncWindow` minutes counted from the last attempt, ask `issue.list` for open issues with `limit`, `since` and `ids` (issues named in a plan's `Blocked On`, `Also Closes` or `Target Issue`, or with an open fix). A returned issue is added or updated by id, no other row's bytes change; one reported `closed` moves to the archive; the issues asked by id stay whatever the limit; of the others at most `aapp.issueCacheMax` stay, those the listing did not bring going first, with a notice when the tracker returned more; a row's plan link and `Planned` status are derived from the plans' `Target Issue`; missing ledger files are created. No description or note is stored by a sync
- a closure made on the tracker reaches the ledger at once: the tracker is the record (#142). It comes in the listing (`status` `closed`, with the `commit` that fixed it, or none) or as `issue close <n> [sha <sha>] summary "…"` in the `do` list; either way the row moves to the archive, also when its commit is not here yet. A plan waiting on the issue is a separate matter and follows the code: it resumes once that commit is in its parent branch (at once when it already is; otherwise at a later `list` or `aapp status`, after the pull), and at once for a closure with no commit (won't fix, a duplicate). A fix open here for the issue is named, to be dropped with `fix <num> abort`
- `list` shows, under an issue's facts line, what the provider called it (`tracker`, `url`, `release`)
- `close`:
    - the row leaves `.plans/ISSUES.md` and is inserted at the top of `.plans/done/000-issues-archive.md` as `| #<n> | Sev | Type | Date Opened | <today> | \`<sha>\` | <summary> |`; a row that names a branch keeps it in the archive's `Branch` column (added when missing, P-78)
    - the `#<n>` entry leaves `.plans/issues_road_map.md`
    - the three files land in one `plans` commit `issue(close): archive #<n>`; nothing else is staged
    - then the provider, if installed, receives `issue.close` once; stdout reports `handed to aapp-issue-tracker: <status>`
- `hotfix`: a new row `| #<n> | \`High\` | \`CORE\` | <today> | <files> | <text> | blocks [<plan>](current/<file>) | 🟡 \`Incubated\` |`; `- [ ] #<n> -> <text> (blocks <plan>)` under `## 🧱 Plan Blockers` at the top of the road map; the plan gains `#<n>` in `* **Emergency Hotfixes:**` (append-only) and is blocked through `plan_block_on` (P-49); over `aapp.maxEmergencyHotfixes` the `Blocked On:` line carries `hotfix limit reached (…)` and only the developer lifts it; one commit `issue(hotfix): #<n> blocks <plan>`; with `plan`, the row is promoted to a new draft (`aapp draft … issue <n>`) and not queued. The row's `Branch` cell (P-78, P-83) has two ways in: every file named is one of the plan's Target Files -> the plan's parent branch (the one in its `* **Base:**`; empty for the development branch); otherwise, or with no file named -> empty, and the fix lands where the `aapp-issue-branch` plugin says, or on the development branch. `branch <name>` writes `<name>` in either case
- `fix`: `current/fix-<num>.md` (Plan ID `#<num>`, `⚡ In Development`, `Changelog: Fixed:` with no text — the fix's first `aapp commit … changelog "<text>"` writes it; nothing is copied from the row, P-66; §4 = the files) and the active buffer bound to `#<num>` with the previous value in `.prev`, one commit `fix(start): #<num>`; `abort` deletes it, restores the buffer, commit `fix(abort): #<num>`
- every fix is made in its own worktree (P-78, P-85): `.workspace/fix-<num>` on `fix/<num>`, cut from the issue's branch also when the main checkout is on it; the mini plan records `* **Base:** \`<sha>\` (<branch>)` and `* **Worktree:** .workspace/fix-<num> (fix/<num>)` and is bound in that worktree (the main checkout's buffer and files are untouched); `next-blocker` claims the top queued blocker; `close` rebases `fix/<num>` onto the branch if it moved, squashes a fix of several commits into one, fast-forwards the branch (in the worktree that has it checked out, when one does), removes the fix worktree and branch, then archives the issue; `fix <num> abort` removes the worktree and branch too
- one commit per fix (P-85): a fix of several commits lands as one commit with subject `fix: <its changelog entry> (#<num>)`, cut at a word boundary with `...` to fit `aapp.subjectMaxLen`, the full entry and the replaced commits' subjects in the body, and the attribution of its last commit (its `AI-*` trailers; its `refs/notes/ai` note and every replaced commit's `refs/notes/commits` note, as at `aapp done`, P-84). A fix of one commit lands with its own SHA. The archive row and `issue.close` name the commit on the branch
- the branch plugin (P-83): for a row that names no branch, `fix` and a `close` with no open fix put the issue and its files to `aapp-issue-branch`. `ok` with `branch` -> that branch, written to the row's cell in the command's own commit (nothing for the development branch), so it is asked once; `declined`, or no plugin installed -> the development branch
- a fix on a group's parent comes back to its feature branch (P-83): at `close`, for each plan blocked on `#<n>` whose parent branch is the feature branch of a group `⚡ In Development`, when the fix commit is in that group's own parent branch, the kit merges the group's parent into the feature branch (the merge the group's `done` makes, never a rebase), stdout `Merged '<parent>' into '<feature>'`; the plan is then unblocked in the close commit and told to rebase. A merge that conflicts is aborted: the feature branch is unchanged, stderr `'<parent>' does not merge cleanly into '<feature>'`, the plan waits. No other branch is merged into: a plan whose parent the team owns, or a fix on a branch that is not the group's parent, waits as below
- a branch that is gone (P-78): when an issue's row names a branch that exists neither here nor on a remote, `fix` and `close` take the development branch instead, clear the cell in their own commit and print `#<n> targeted <branch>, which no longer exists; it now targets <dev>`; nothing is refused
- unblocking follows the code (P-78): `close` unblocks a plan waiting on `#<n>` only when the fix commit is reachable from the plan's parent branch (the development branch for a plan never started). Another plan keeps `#<n>` in `Blocked On:` and stderr names it: `<plan> stays blocked: #<n>'s fix (\`<sha>\`) is not yet in its parent branch '<parent>'`; `aapp status` unblocks it once the commit is there. The fix is recognised by its commit only: after a squash merge made by hand, a cherry-pick or a rebase the plan stays blocked until `aapp refine <plan> unblocked <num>`. The kit's own squash is recognised: `aapp done` squashes on the plan branch and records that commit, which the parent is fast-forwarded to (P-84)
- `close` of an issue with an open mini plan: checks limits and declared files before landing (P-82): any changed file outside the issue row's Location and declared Target Files is refused; exceeding `aapp.fixMaxFiles` (default 3) or `aapp.fixMaxLines` (default 25; added + deleted lines across fix files, excluding CHANGELOG.md) refuses landing with both numbers and directs to `aapp issue fix <n> abort` then `aapp draft <slug> issue <n>` (0 turns off a limit). The SHA defaults to the commit the fix landed as and the summary to the fix's changelog entry (`<entry>; unblocks <plan>`, P-66); the mini plan is deleted and the buffer restored; any plan whose `Blocked On:` lists `#<n>` drops it and, once empty and not permanent, gets its recorded status back; the matrix is re-derived; all in the one close commit (the same unblocking runs when `aapp done` closes a Target Issue); stdout then prints `ℹ️  <plan> also lists <file>: it picks this fix up at its next rebase.` for every other ⚡ or BLOCKED plan whose Target Files include a fixed file (output only, P-58)
- `fix` without `group`: when an active group's feature branch differs from the development branch in the fix's files, stdout adds `Group <id> changes these files on '<branch>'` with `aapp issue fix <num> group <id>`; the fix still opens, the human decides (P-64)
- `fix … group <group>`: the mini plan records `* **Worktree:** .workspace/fix-<num> (fix/<num>)` and `* **Group:** <group>` and is bound in that worktree (the main checkout's buffer is untouched); `close` rebases `fix/<num>` onto the feature branch if it moved, fast-forwards the feature branch, removes the worktree and branch, then archives the issue as usual (P-64)
- `abort`:
    - what was opened for the issue goes first, through its own code and commit: its plan by `aapp plan abort <id> reason "Issue #<num> aborted: <reason>"`, its open mini plan as `fix <num> abort` drops it
    - then one `plans` commit `issue(abort): withdraw #<num>`: the row moves to the top of the archive with `` `aborted` `` as its *Target Commit / Release* and `Aborted: <reason>` as its summary, followed by `([P-<id>](../aborted/<file>))` when its cell links an aborted plan; its road-map line goes; plans blocked on it resume as on `close`
    - a run interrupted after the plan went leaves the issue open and 🟡 `Incubated`; running `abort` again withdraws the row
    - the provider is not notified: `issue.close` reports a fix
    - a withdrawn issue has no commit: the branch rules do not apply, and every plan blocked on it resumes whatever its parent branch (P-78)
    - the other direction never withdraws an issue: `aapp plan abort` and `fix <num> abort` leave it open
- the work queue (P-89): `.plans/issues_road_map.md` has two sections, `## 🧱 Plan Blockers` (written by `hotfix`) and `## 📋 Queued` (written by `queue`) with its three levels `### 🔺 Urgent`, `### Normal` and `### Low`, oldest first in each; `fix next-blocker` takes the top blocker, then the queued issues level by level (a `Planned` one is skipped: its plan fixes it). `queue` sends `issue.queue`, `queue … remove` sends `issue.unqueue`, with the whole issue. Where a tracker keeps the record its queue is the queue: the listing's `queued` field (`true` or `false`), with `priority` (`urgent`, `normal` or `low`; `normal` when absent) and `queued_at`, rebuilds the three levels at every sync, in the listing's order inside each; `issue.queue` carries the level as `priority`; without one, a failing step only warns
- `list` and the Issues pillar of `aapp status` (P-89, P-93): each issue as a facts line at 2 spaces, `#<n>  <Sev>  <Status>  logged <date>`, followed only by the facts it has: `queued <date> (<Level>)`, `[<plan>]` (`[blocks <plan>]` for a hotfix), `(branch: <name>)`, `offline` (staged in `.offline`), `<n> notes` (`1 note`: the description and notes `list note <num>` and `fix` show; none printed here); two spaces between facts, no padding. Then the tracker's names on a line of their own at 8 spaces, `· <tracker> <url> (<release>)`, when a provider gave them, and the symptom wrapped at 8 spaces. No line is wider than `aapp.statusOutputWidth`; no blank line between issues. `list` shows the symptom whole; the Issues pillar cuts it at `aapp.statusTextMax`. Severity, status, the logged date and the plan come from the row, the queue date and level from the work queue
- the records (P-92): `list` and the Issues pillar print the records of `ledger_issue_records` (`lib/aapp-lib.sh`), one per active issue: `id`, `severity`, `type`, `status`, `logged`, `location`, `symptom`, `plan`, `blocks`, `queue_section`, `queue_level`, `queued`, `branch`, `offline`, `tracker_name`, `tracker_url`, `tracker_release`, `notes`. `notes` counts the description and notes the kit's store keeps, and is empty where an `aapp-issue-tracker` provider is installed (it may keep them); no text of a description or note is in a record
- `list`: every active issue in the order `ISSUES.md` records it, then those staged in `.offline`; once an open issue names a branch, each facts line has `(branch: <name>)` (the development branch for an issue that names none) and the issues of the current branch (in a plan's worktree: of the plan's parent branch) come first (P-78); a truncated list ends with `… <k> more (aapp issue list all)`
- `aapp done` on a plan whose Target Issue is `#<n>` performs the same `close` in its own archive commit; a Target Issue in neither ledger refuses `done` before anything moves. Other plans blocked on `#<n>` resume under the same rule (P-78): at once when the plan's commit is already in their parent branch, otherwise after `done` integrates the plan branch, or at the next `aapp status` once the commit is there

## Exit
- 0 on success, including an already-archived `close` and a provider that fails on `close`
- non-zero on invalid arguments, a corrupt counter, a failing provider on `log` or `next-blocker`, a refused switch to a tracker-kept record, or an unknown id
